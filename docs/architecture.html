CRM Help Bot Architecture

A help chatbot inside the CRM that answers “how do I…” questions from product documentation, with citations. It answers only from the CRM modules each user is licensed for. Ops admins upload versioned docs, publish them through an automatic safety gate, run evals and watch LLM cost per client company.

01Decisions at a glance

Store One Postgres: pgvector + full-text search ~100 docs → exact vector search. Module filter inside every query. ADR-0001
Keyword search Postgres full-text, fused with vectors by RRF Real BM25 (pg_search) only if keyword-recall evals ask for it. ADR-0001
LLM provider OpenRouter in development, Bedrock in production Bake-off only compares models available on both, so results carry over. ADR-0002
Background work A job queue in Postgres, one worker No Redis or broker for a few jobs a day. ADR-0003
Who controls access Modules come from the doc’s frontmatter only Publishing goes through an automatic gate; any widening of access needs a person to confirm. ADR-0004
Cost Estimated per LLM call, per client and per chat Tokens × a dated price table. No message text kept in cost records. ADR-0005

Assumptions. If any of these is wrong, the design changes.
  1. Docs are our product documentation, shared by every client company. Clients don’t upload their own.
  2. All client companies run the same CRM release (confirmed), so keeping edit history is enough.
  3. At most about 100 docs, roughly 3,000–5,000 chunks.
  4. Production runs on AWS.

03System overview

Two front ends, one API, one worker and one database. Every permission decision happens in the API and inside the database query, never in a prompt.

04Query path

The same pipeline as the walking skeleton built in M0.1–M0.3, with the mock responder replaced step by step. Two steps are new.

  1. Conversation ownership. A conversation ID must belong to the caller, otherwise the server answers 404. A missing ID gets a new server-created conversation.
  2. Validate the JWT; resolve allowed modules on the server.
  3. Input guardrails; redact PII before anything is stored.
  4. Rewrite follow-ups into a standalone question, split cross-module questions (small model).
  5. Hybrid search for each sub-question, module filter inside the query, fused by rank.
  6. Rerank, keep module diversity, expand to the parent section.
  7. Weak match: a templated refusal with no LLM call.
  8. Generate the answer from a versioned prompt.
  9. Drop any citation that wasn’t in the context.
  10. Stream events to the widget.
  11. Record one cost row per LLM call, the trace and the redacted message.

Hybrid retrieval

Two searches run side by side and are fused by rank. Both apply the module filter before ranking, so a restricted chunk is never a candidate. Modules are the only metadata filter. There’s no upload-date filter: only the latest published version of a doc is searchable at all.

-- per (sub-)question; :allowed = the caller's resolved modules
vec AS (SELECT chunk_id, row_number() OVER (ORDER BY embedding <=> :qvec) r
        FROM live_chunks WHERE modules <@ :allowed ORDER BY embedding <=> :qvec LIMIT :k),
kw  AS (SELECT chunk_id, row_number() OVER (ORDER BY ts_rank_cd(tsv, q) DESC) r
        FROM live_chunks, websearch_to_tsquery('english', :qtext) q
        WHERE modules <@ :allowed AND tsv @@ q ORDER BY ts_rank_cd(tsv, q) DESC LIMIT :k)
SELECT chunk_id, sum(1.0 / (60 + r)) AS rrf          -- reciprocal rank fusion
FROM (SELECT * FROM vec UNION ALL SELECT * FROM kw) u GROUP BY chunk_id ORDER BY rrf DESC

05Content lifecycle

Admins upload markdown. Each upload is a new, immutable version of the doc. Nothing changes for chat users until someone publishes a release: a complete new search index built from a chosen set of document versions, promoted only if the gate passes. Rolling back points the index at the previous release.

The publish gate

Automatic, with no LLM calls, on every publish:

Zero tolerance

Permission suite. For every persona and every eval question, each retrieved chunk’s modules must be within that persona’s allowed set. One leak blocks the release. It needs no labelled answers, so it protects brand-new docs too.

Threshold

Retrieval evals. Recall@k and complete recall@k may not regress beyond threshold compared with the live release.

Blocks

Orphaned eval labels. An eval question pointing at a section that no longer exists (a renamed heading) blocks publishing until an admin re-points it.

Needs a person

Access widening. If a doc’s modules change so that more users can see it (for example Deals → shared core), a publisher must confirm. The confirmation is audit-logged. Narrowing access passes automatically.

Modules come only from each doc’s frontmatter. The admin app has no module assignment in the MVP, so the doc stays the single source of truth for access.

06Observability and cost

Phoenix, for engineers

  • OpenTelemetry spans for every request and job
  • Retrieval candidates, rerank scores, redacted prompts, latency per stage
  • For debugging; not shown to admins

llm_calls, for admins

  • One row per LLM call: client company, conversation, stage, model, tokens, cost
  • No message text, so it’s kept long-term
  • The cost dashboard reads only this table

Estimated cost = tokens × the model price in effect at call time. Prices are dated, so past costs never change.

-- per client company, per month
SELECT tenant, date_trunc('month', created_at), sum(cost_usd) FROM llm_calls WHERE bucket = 'chat' GROUP BY 1, 2;
-- per chat session
SELECT conversation_id, sum(cost_usd) FROM llm_calls GROUP BY 1;
BucketWhat it coversCharged to a client?
chatQuestion rewrite and answer generationYes
evalEnd-to-end eval runs and the LLM judgeNo, internal
ingestSynthetic eval-question generationNo, internal

Embedding and reranking run on our own compute and count as infrastructure, not per request. Privacy: PII is redacted before storage, including traces. Message text is kept 30 days. In the MVP only ops admins can see transcripts. Letting a client company’s admin see their own users’ chats is planned for later: every conversation already records its client company, so it needs a client-scoped admin role, a filter on that company in every transcript query, and a notice to users.

07Evals

LayerRunsUses an LLMBlocks publishing
Permission suite: retrieved chunks stay within allowed modules, across all personas and random entitlement setsEvery publish and CI runNoYes, zero tolerance
Retrieval: recall@k, complete recall@k, MRREvery publishNoYes, threshold
End-to-end: faithfulness, correctness, refusals, citations, scored by an LLM judgeManual, from the admin appYesNo, reported

End-to-end evals can’t stand in for the permission suite. If a restricted chunk reaches the prompt and the model happens not to mention it, an end-to-end eval passes even though a leak occurred.

Where questions come from

  • Written by admins in the UI, against sections of the live docs
  • Generated synthetically per doc by a different model than the answer generator; they arrive as proposed and count only once an admin accepts them
  • Every successful red-team attack
  • Imported from the golden YAML files

Calibrating the judge

  • Admins label a sample of end-to-end answers as faithful and correct
  • Each run reports how often the judge agrees with the admin labels
  • Plan on 50–100 labels before trusting the judge’s scores

08Models

Start with the smallest model that passes, and move up only when evals say so. The judge is the exception: it must be strong, and from a different vendor than the answer model.

RoleStarting pointRule
Rewrite and split questionsSmallest model with reliable structured outputFalls back to the raw question if the output fails validation
Answer generationBake-off, smallest candidate firstNo reasoning models; pinned versions only
LLM judgeA strong modelDifferent vendor from the answer model
Synthetic questionsAny capable modelDifferent from the answer model

OpenRouter in development, Bedrock in production. The bake-off only compares models offered on both, and OpenRouter is pinned to each vendor’s own endpoint with fallbacks off, so results carry over to production. Only synthetic docs and users go to OpenRouter. Real questions can contain personal data and real docs are confidential, so once real content arrives, development moves to Bedrock, which the production AWS agreements already cover.

Production compute to settle: the reranker scoring 30–50 candidates on CPU takes 1–2 seconds. Options: a small GPU instance, a lighter reranker, or Cohere Rerank on Bedrock. The bake-off’s latency numbers decide.

11Build order

The admin work slots in between the existing pipeline stories. IDs are placeholders.

  1. A1 Content store. Docs, versions, and upload with validation. Builds on fail-closed validation (S2.1.1).
  2. A2 Releases and the worker. Build, gate, publish and rollback. Reuses chunking and embedding (S2.1.2, S2.1.3) and the permission suite (S2.3.2).
  3. A3 Admin app shell. Sign-in, roles, and the Documents and Releases screens.
  4. A4 Cost accounting. Cost rows, price table, server-owned conversations, Costs screen. Follows tracing (S3.1.4).
  5. A5 Eval workflow. Authoring, synthetic proposals, the end-to-end run button and labelling. Builds on S2.3.1 and S3.2.1.

12Open questions

Source of truth: docs/architecture.md in the repository, with decisions in docs/adr/0001–0005. Rules this design must never relax: permissions come only from the verified token, filtering happens inside the query, restricted content never enters the prompt, and the system fails closed.
